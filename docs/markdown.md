# Markdown access

Every published localized article has a static Markdown representation:

```text
/en/posts/nitp/           HTML
/en/posts/nitp/index.md   Markdown
/zh/posts/nitp/index.md   Chinese Markdown
```

These files and `/llms.txt` are generated by `npm run build` from the content collection. Nested translation slugs work the same way. `/llms.txt` lists each real language version once and links to the localized archives, feeds, and sitemap. It is an additional discovery aid, not an access-control policy or a guarantee that every agent will use it.

Article HTML includes a Markdown alternate link and a visible localized link. The shared layout links to `/llms.txt` with `rel="describedby"`.

Markdown frontmatter includes the title, author, date, description when present, actual language, canonical HTML URL, and existing translation. English fallback routes export the Chinese original with a translation notice. Drafts never provide an export or a translation counterpart. Links are absolute; source-relative content images are emitted as public assets. The Markdown parser preserves code and math content while normalizing Markdown formatting. Raw HTML image tags remain HTML with absolute source URLs.

## Content negotiation

The Nginx configuration in `infra/nginx/blog.conf` serves the same Markdown file when an article request explicitly accepts `text/markdown`:

```sh
curl -fsS https://blog.konakona.dev/en/posts/nitp/index.md
curl -fsS -H 'Accept: text/markdown' https://blog.konakona.dev/en/posts/nitp/
```

The server prefers Markdown when it is explicitly accepted with nonzero quality, including in a mixed Accept header. It serves HTML for absent or wildcard-only Accept headers and when Markdown has `q=0`. Both representations at the canonical article URL carry `Vary: Accept`. Explicit `index.md` URLs always serve Markdown, independent of Accept. Article archives and the language redirect keep their existing behavior. Unknown article and Markdown URLs return 404.

Markdown responses use `Content-Type: text/markdown; charset=utf-8`. Astro dev/preview can serve explicit Markdown URLs; content negotiation is implemented by Nginx.

## Deployment

The normal GitHub Actions deployment publishes the generated files. It does **not** update Nginx. The Markdown additions to the repository configuration have not yet been applied to production.

When applying the server changes, back up the active configuration at `/etc/nginx/sites-available/blog.konakona52.com.conf`, apply the repository changes, run `nginx -t`, and reload after validation. The `map` directives belong in the HTTP context, where the sites configuration is included. Keep the repository mirror current and remove its pending-application comment after applying the change.

Check the CDN as well as the origin: responses with different Accept headers must not share the wrong cached representation. If a CDN rule caches article HTML without varying on Accept, bypass caching for those article URLs or configure a representation-aware cache key before enabling negotiation. Explicit Markdown URLs work independently of that configuration.

## Verification

`npm test` builds the site and checks all exported routes for metadata, discovery links, reachable local assets, and preservation of code, math, and tables. It also verifies that Markdown alternatives stay out of the HTML sitemap.

To run the real Nginx response checks, provide a local Nginx binary:

```sh
NGINX_BIN=/path/to/nginx npm test
```

The Nginx checks run an isolated HTTP server on a temporary local port using the repository's maps, headers, and article locations. They check direct and negotiated responses, quality-zero exclusions, nested routes, 404s, conditional requests, and HTML defaults. They do not modify a running server or validate the production CDN configuration.
